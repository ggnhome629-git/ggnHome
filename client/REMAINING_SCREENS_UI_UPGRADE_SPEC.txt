================================================================================
GGNHOME - REMAINING SCREENS UI + FUNCTIONALITY UPGRADE SPECIFICATION
================================================================================
Scope: every screen not yet redesigned (the admin panel has its own spec in
ADMIN_PANEL_UI_UPGRADE_SPEC.txt, the property detail page in UI_UPGRADE_GUIDE.txt).
No existing feature is removed. Each screen lists: CURRENT (read from the code),
UPGRADE (UI), FUNCTIONALITY (behaviour), and the reason (what high-traffic
sites do and why users like it).

Research basis and honesty note
- Patterns come from web searches on real-estate portals (Housing.com, Zillow,
  Matterport, 99acres/MagicBricks/NoBroker were searched but their own UIs are
  mostly behind scripts, so claims below are limited to what the search results
  and public help pages actually said) plus general UX literature.
  Sources are listed in PART 12. Nothing here was measured on ggnHome traffic.
- "[API OK]" = backend call already exists. "[NEEDS API]" = new backend work.
- Priority: P1 = do first (high traffic or conversion), P2 = next, P3 = polish.

Build rules for ALL screens (so they match the redesigned pages)
- Reuse the navy/teal system already used on Dashboard, Search, Flatmates and
  Post forms: theme tokens, SectionShell, rounded cards, 8px spacing grid.
- Mobile first. 16px side gutter, no horizontal scroll, tap targets >= 44px.
- One top navigation per audience (user / agent / flatmates) - no screen builds
  its own header (Customer Support currently hand-builds a fixed navbar).
- Every screen has explicit loading (skeleton), empty, error and success states.
- Remove inline COLORS objects and inline <style> blocks; use the shared theme
  (userpreferenceform.jsx defines its own palette today).
- No alert(); use one toast/snackbar component. No console.error-only failures.
- Accessibility: visible focus ring, labels tied to inputs, aria-live for
  errors, 4.5:1 contrast, prefers-reduced-motion respected.
- Analytics events on each primary action (see PART 11).

PART 1 - LOGIN / SIGN-UP            client/src/screens/Login Page/login.jsx (841)  P1
================================================================================
CURRENT
 OTP request/verify by mobile, resend, password login, set password,
 check-mobile, recovery email. Fields: Mobile, Email, Password, Confirm.
 Calls: /login/request-otp, /login/verify-otp, /auth/check-mobile,
 /auth/set-password, /login/password, /auth/set-recovery-email.

UPGRADE (UI)
 1. One-field-first screen: only "Mobile number" with +91 prefix and a single
    primary button "Get OTP". Everything else appears after. Fewer visible
    fields at the start lifts completion (UX literature on signup patterns).
 2. Segmented choice under the button: "Use password instead" / "Use email OTP".
    Equal visual weight - a fallback must never look like a dead end.
 3. OTP screen: 6 separate boxes, numeric keypad on mobile, auto-advance,
    paste-the-whole-code support, "Edit number" link, resend timer
    ("Resend in 28s"), and a "Didn't get it? Try email / call me" fallback.
 4. Auto-fill: input autocomplete="one-time-code" and inputmode="numeric" so
    the phone offers the SMS code automatically (Twilio OTP form guidance).
 5. Left/top trust panel on desktop: 3 benefits ("Verified owners",
    "Rewards on every visit", "No spam"), a privacy line, and a Gurgaon-first
    badge. Collapses away on mobile.
 6. Inline validation as you type (10 digits, starts 6-9), green tick when
    valid, red message with fix hint when not. Never clear fields on error.
 7. Password creation: strength meter + show/hide eye + rules checklist.
 8. Return the user where they came from (save/enquire/schedule intent) and
    show "Continue saving this home" after login.

FUNCTIONALITY
 - Rate-limit messaging: "Too many tries - try again in 10 min" from server
   status 429 instead of a generic error. [API OK]
 - Remember last used method (OTP vs password) in localStorage.
 - "Logging in as +91 98xxxxx210" masked echo on the OTP step.
 - Optional Google sign-in as a shortcut, never the only path (UX pattern from
   Housing.com help: phone + OTP, or Gmail). [NEEDS API]
 - Account-exists detection already via check-mobile: show "Welcome back" vs
   "Create your account" headline accordingly.

WHY: Housing.com's published flow is phone + OTP with an alternative; the
dominant failure is OTP not arriving, so resend, fallback and auto-fill matter.

================================================================================
Read from server/Route/route.js (442 lines), models/ and controllers/.

13.0 GAPS FOUND IN THE CURRENT SERVER (fix first)
 G1  No rate limiting anywhere (no express-rate-limit in package.json or
     index.js). OTP request/verify, password login, callback and enquiry
     endpoints can be hammered. Add per-IP and per-mobile limits.
 G2  CustomerSupport model has no status, ticket id, user link, reply or
     source field; all fields required (email required even for phone-only
     users). /api/request-callback needs login (verifyToken), so guests on
     the Support page cannot submit.
 G3  No Visit/Booking model or endpoint. "Schedule visit" has nowhere to
     store slots, owner response, reminders or cancellations.
 G4  Service requests have only pending / in-progress / completed; no
     cancelled, vendor, price, photos, rating, timeline or invoice.
 G5  Enquiry has a 45-day TTL index and no status/reply; owners cannot mark
     it contacted/closed from the app.
 G6  UserPreferenceForm POST (/api/userpreferenceform) is public and
     unthrottled: spam and fake leads. Needs rate limit + OTP-verified mobile
     or login. Fields budgetRange, bhkSize, moveInDate are free strings, so
     matching is fragile.
 G7  Payment model has no link to a visit/booking, no gateway order id, no
     refund state, and paymentMethod is a loose enum. status lacks "refunded".
 G8  Admin usage endpoints (/api/admin/cloudinary|brevo|mongo|gnews|locationiq
     /usage) have NO auth middleware in route.js; anyone can call them (they
     expose account usage). /api/locationqapi hands out the LocationIQ key to
     any caller. Add verifyToken + checkAdminEmail to the usage routes.
     (/api/admin/delete-property/:id only has verifyToken in the route, but
     the controller itself rejects non-admins, so that one is fine; moving the
     check into route middleware would still be cleaner.)
 G9  No central input validation (use zod/joi/express-validator) and no
     consistent error shape {code, message, fields}.
 G10 No pagination contract on list endpoints (services, enquiries, admin
     lists); only search exposes X-Total-Count.
 G11 No audit log (who approved/deleted/changed what) for admin actions.
 G12 No notification layer: SMS/email sends are called inline. Need one
     notify(user, template, data) service with queue + retries + logging.
 G13 CORS in dev: fixed in index.js this session (localhost any port when
     NODE_ENV != production). Keep ALLOWED_ORIGINS exact in production.

13.2 NEW / CHANGED ENDPOINTS (by screen)
 AUTH (Part 1, 2)
   POST /auth/otp/resend            resend with cooldown, returns nextAllowedAt
   POST /auth/otp/email             send OTP to recovery email as fallback
   POST /auth/otp/voice             optional voice-call OTP fallback
   GET  /auth/methods?mobile=       which methods exist (otp/password/google)
